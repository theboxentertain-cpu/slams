## Security and deletion resolution

The checked-in private-row policies use authenticated owner checks for reads/writes/deletes; update policies also prevent owner reassignment. The import path confirms full owner-scoped persisted copies before local removal and re-reads current storage. These mechanisms remain untouched in PR A.

The local SQL audit uses two **simulated database identities**, not two independent live email-confirmed Supabase accounts. Its result must not be presented as deployed RLS or full authentication verification. Curriculum tables currently have public read policies; review/publication gates restrict completion, and no confidentiality/paywall guarantee is claimed for draft teaching rows.

Proposed orphan resolution for a later reviewed engineering change: inventory affected rows using read-only owner joins; back up before any retention action; agree a legal/product retention policy; restrict access to any retained archive; add and validate owner FKs only after preserving/resolving existing rows; test auth deletion, ordinary owner operations and rollback in disposable PostgreSQL. A rollback that merely drops a cascade FK cannot restore deleted data, so restoration requires the preserved backup. No destructive migration, archive or cascade was applied here. The earlier separate deletion-proposal branch is not presumed merged into main.
